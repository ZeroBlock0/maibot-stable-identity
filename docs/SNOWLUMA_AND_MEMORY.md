# QQ 身份、SnowLuma Adapter 与长期记忆

核对基线：MaiBot 1.3.15、SDK 2.16.0、SnowLuma Adapter 1.1.9（本地提交 `ab751ae5c11f501e0158e33cacc321b33e34ef0c`）、本插件 0.2.0。这里只说明已读取的本地版本，其他版本未验证。

## 是否应该使用 SnowLuma 的 QQ ID

应该使用平台上报的真实发送者 QQ 号，本插件已经如此设计：

```text
QQ 客户端事件 user_id
  → Adapter message_info.user_info.user_id
  → 宿主原始消息记录（含平台、机器人账号、路由、会话、原始消息 ID）
  → 插件核验原始记录
  → 模型外层 sender_id="qq:真实账号"
  → 正式 person.get_id 关联宿主 person_id（同账号单次请求仅标一次）
```

Adapter 的 `codecs/inbound/message_codec.py:QQInboundCodec.build_message_dict` 把真实发送者 ID放进 `user_info.user_id`，同时保留昵称、群名片、原始消息 ID；`runtime/router.py:QQEventRouter.handle_inbound_message` 补上机器人 `account_id` 和连接 `scope`。NapCat 和 SnowLuma 两种客户端都走这条链路。

“哪个人”的主键是平台＋用户 ID；“在哪个范围能查询”的权限还要包含机器人账号、连接、群/私聊会话。不能因为某个人 QQ 号相同就把其他群或私聊的内容带进当前查询。

无须为每条消息再次调用查 QQ 号工具。Adapter 自带 `find_user_qq_id(msg_id)`，仅在模型调用时查询指定消息发送者；它不会自动给所有历史打标签，也不会重新整理记忆。插件当前不额外调用该工具或 Adapter API，不依赖它的可选查询能力，缺失原始记录时保持未知。将来若加补证，还需核验消息实际会话、机器人账号和路由，不能直接拿一个 ID查询结果跨群回填。

## 两者分工与配合

| 能力 | SnowLuma Adapter | 稳定身份增强插件 |
|---|---|---|
| QQ 通信、收发和群成员接口 | 负责，支持 SnowLuma/NapCat | 使用宿主已经接收的消息 |
| 原始消息带真实发送者 QQ 号 | 负责上报 | 核验并保留其原有含义 |
| Planner/Replyer 逐条显示稳定身份 | 未在此版本发现此功能 | 能准确回查的结构化消息均标注 |
| 根据指定消息查发送者 | `find_user_qq_id` 按需查询 | 同会话原话工具可返回发送者和原文证据 |
| 按用户、关键词、时间查询原话 | 此工具不是这项功能 | 当前授权单会话内查询 |
| 长期记忆归属和来源 | 不能由适配器独立保证 | 桥接 person_id；原生工具记录有完整结构时核验主体和来源，其他路径仍受接口限制 |

可以配合：Adapter 接收并上报真实身份，插件把宿主记录里的身份明确呈现给模型。不需要替换 Adapter、不改原生人设或原生工具。Adapter README 所说的“napcat/snowluma 画像”是客户端协议能力配置，不是群友的人物画像或长期记忆。

## 哪些数据持久化

| 数据 | 当前保存方式 | 重启后 |
|---|---|---|
| 插件启停、版本、容量限制 | 插件 `config.toml` | 保留 |
| 插件身份/短 ID映射、人物缓存、计数 | 有容量和过期限制的内存缓存 | 清空；从宿主重新核验 |
| 原话查询上下文和一次性凭据 | 内存，默认两分钟有效 | 失效，不能重放 |
| Planner→Replyer 记忆来源引用 | 内存，最多 256 个/两分钟，绑定会话及路由 | 失效，无引用不猜测继承 |
| 原始聊天记录、宿主人物数据 | 宿主已有数据库；插件不复制或修改 | 取决于宿主原有保存和清理策略 |
| 原生长期记忆与人物画像 | 宿主原有系统；插件不迁移、不重建 | 原有数据保留，原有归属错误也可能保留 |
| 临时请求中的身份前缀 | 当前请求；宿主快照可能继承 | 若宿主保存推理/请求快照，标记可能随快照落盘 |

插件卸载没有自己的聊天或记忆数据库需要清理。删除插件不批量改写宿主已有快照或记忆。

## “对话认人”和“回想认人”的实际边界

对话路径已实现逐条原始账号核验和原话查证。但复古历史模板缺少逐条 ID，只能补明确的回复目标；部分压缩追加资料绕过 Hook；Focus 共享请求的新增查证没有唯一会话授权，因此拒绝执行。模型也可能忽略标签，所以不能保证绝不认错。

人物画像方面：已核验消息带有通过正式 `person.get_id(platform, user_id)` 获得的 `person_id`（同账号单次请求仅标一次），支持显式 `person_id` 的原生画像工具可使用它。插件没有把旧人物画像或每条旧记忆重新标成某个 QQ 号，也没有强制替换原生昵称解析。

长期记忆方面，当前源码的两处限制已经核对：

1. `src/A_memorix/core/runtime/services/search_hit_processing_service.py:_filter_hits` 的 `return filtered or hits` 会在人物过滤无匹配时退回原候选；它还接受正文里出现 person_id，不是可独立认证的事实归属。
2. `src/plugin_runtime/capabilities/data.py:_cap_knowledge_search` 向插件返回拼接文本，未提供逐条命中人物、来源会话及原始消息引用，插件无法对每条结果再次做身份和来源校验。

因此“两个插件一起用”仍不能承诺长期记忆绝不串人。插件只补可靠的当前账号/人物关联，并让模型用原话工具核实有原始记录的问题；不会把没有来源的旧摘要包装成原话证据。

0.2.0 已增加一条正式接口内的部分接入：通过 database.get(ToolRecord) 回查当前原生记忆/画像工具的记录。有完整 structured_content 时核验每条命中的真实主体、会话及原始来源，并用明确引用交给 Replyer 重新检查。宿主省略结构时明确 structured_omitted，不能从摘要恢复。详见 [记忆增强说明](MEMORY_BRIDGE.md)。

## 完整记忆接入所需的正式接口契约

要使新记忆也可靠区分人物，还需要记忆写入、检索和模型注入三层共同支持，不能只给查询提示加 QQ 号：

- 写入：每项人物事实记录稳定的主体 ID，另存原始发言者 ID、来源消息 ID、时间和会话归属。发言者与事实主体分别记录；甲转述乙的经历不能直接写成甲的事实。原话只证明某账号这样说过，不保证所述事实为真。
- 检索：SDK 提供结构化命中，含主体、来源及可核验权限范围。按人物筛选未命中就返回空；无法归属的结果明确 unknown，不能回退成其他人的记忆。
- 注入：画像/回想给模型的每条事实携带稳定人物标记和来源；原始消息已删除或无权访问时明确证据不可用，不能绕开权限跨群取原文。
- 旧数据：保持原样；只有能准确回查来源的条目才有补证可能。没有来源的不自动归属，不按昵称或向量相似度批量修正，不承诺旧错误记忆自动恢复。

这是后续宿主/SDK 能力的明确需求，当前插件未实现这些接口，没有修改主程序、调用内部远程服务或替换原生方法。需要改宿主时，应先遵循主程序 AGENTS.md 的许可要求，再遵循 A_memorix 的修改策略。

## 实际验证范围与查看日志

0.1.2 的合成测试实际执行本地 Adapter 的入站路由与消息编码函数，网络、客户端和宿主存储为替身。两个客户端画像都验证了同名两人、同人改名和正文伪造 ID经过两条模型请求 Hook 后仍使用真实发送者 QQ 号，并经过真实宿主参数替换与反序列化。不是在线 QQ/WebSocket 验证。

用户提供的部署日志显示旧版虽有 verified 计数，但 Planner/Replyer 多次因丢失 `item_schema_version` 而忽略结果。0.1.2 修复完整参数回写；新测试特意复现旧错误，再验证新版被当前宿主协议接受。不能把旧版计数当作成功证明。

日志筛选 `plugin.local.stable-identity` 或 `身份增强`。新版在 INFO 输出加载、入站、Planner、Replyer 及原话查询摘要；同类活动每阶段首次立即输出、后续每 60 秒限频，未知为 WARNING。若宿主全局过滤高于 INFO，活动摘要也会被过滤；插件不擅自改变全局日志等级。历史 `verified` 是重复处理的累计条数，不是唯一群友数，也不是供应商接收确认。

上线确认需要同时看宿主拒收告警与最终请求前缀。0.2.0 已做合成测试及授权导出的只读记录回放，尚未在用户真实运行实例验证，最终第三方插件组合及模型实际行为仍须部署后检查。
