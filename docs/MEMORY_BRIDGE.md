# 原生记忆主体与来源核验（0.2.6）

这是独立插件内的只读增强，适用于本地核对的 MaiBot 1.3.15、SDK 2.16.0。没有新增记忆数据库、替换原生处理器、改变原生工具参数或启停其他插件。身份、原话和记忆核验均不额外调用模型。

## 已实现的三条链路

1. 原话工具支持 `person_id`：通过正式 `database.get(PersonInfo)` 反查当前平台真实账号，再用 `person.get_id` 核对。与 `sender_user_id` 同填时必须一致。昵称不参与身份推断。
2. 原话工具支持 `message_ids`：一次查询 1–12 个来源 ID，和单个 `message_id` 互斥。显示短 ID只用本次冻结映射展开；缺失和冲突不猜测。返回每条原文的账号、person_id、时间及类型；缺失 ID另列 `missing_message_ids`。空数组拒绝，不会悄悄变成宽泛搜索。
3. 模型请求中的原生 `query_memory` / `query_person_profile` 结果，可以通过正式 `database.get(ToolRecord)` 回查结构化记录，并增加独立 System 说明。原工具调用、输出、调用 ID和配对保持不变。

这不是新增一个全库记忆搜索工具。检索和写入仍由原生功能决定，插件只核验明确进入当前上下文的结果。

## 来源必须满足的条件

工具记录必须在当前可信 Hook 会话内按 call_id 唯一找到；记录的工具名、会话、stream_id、call_id、原生提供方及 history_content 摘要必须与实际工具输出对应。不会解析用户正文中伪造的 ToolResult、person_id 或消息标签。

对于每条记忆命中，分别检查：

- `metadata.chat_id` 及 `chat_ids` 能明确限定当前会话；跨会话或无法确认的范围不补身份。
- `metadata.person_ids` 恰好有一个稳定主体，其他主体字段与之不冲突；不能把查询请求的 person_id 当成每条结果的主体。
- 主体能从正式人物表映射为真实账号，并在当前会话有归属一致的原始记录；不额外暴露其他群人物表中的账号信息。
- `evidence_message_ids` 使用原始 ID逐条回查当前会话，核对唯一性、平台、机器人账号、路由、通知类型和来源发言者。机器人发言明确标为 bot，引用和转发不能变成当前发言人的经历。

核验说明不复制记忆正文或引用内文，只给主体账号映射、来源 ID/时间/发言者及状态。原话需通过原话工具按权限查询。

| 状态 | 可以得出的结论 |
|---|---|
| `source_identity_verified` | 已回查的来源消息身份与该记录的主体一致；不代表事实内容真实或语义提取正确 |
| `evidence_incomplete` | 有主体映射，但原始证据缺失、发言者不同、记录冲突、范围不符或未保存来源 |
| `subject_unknown` / `subject_conflict` | 无法可靠确定该条结果主体，不按名字补全 |
| `profile_subject_mapped` | 原生工具报告的画像人物 ID能映射到当前会话账号；画像工具没有暴露逐条原始证据 |
| `structured_omitted` | 宿主明确省略了结构化结果，插件无法从摘要恢复人物和来源 |
| `record_unavailable` / `record_mismatch` | 没有唯一可信的原生工具记录，或其内容与当前工具结果不一致 |
| `scope_mismatch` / `unknown_scope` | 当前会话范围不符或 Focus 共享 Hook 没有唯一授权范围 |
| `reference_unavailable` | Replyer 没有可用的本次明确引用；不继承最近一次查询 |
| `reference_missing` | 仅日志诊断；非空参考没有核验引用或原生工具结果，本次补充层未核验，不表示原生工具没有运行 |
| `budget_exhausted` / `not_checked` | 本次核验预算不足，未核验部分保持未知 |

人物检索降级返回别人候选时，插件按每条命中自己的元数据和来源标记实际主体，并显示 `matches_query_subject=false`；不把它改标为最初查询的人。原生检索结果仍原样保留，不会被插件偷偷过滤或重排。

`subject_unknown.reason` 进一步区分缺失层，日志显示对应的 `reason_...` 计数：

| 原因 | 含义 |
|---|---|
| `missing_subject_ids` | 记录没有人物 ID；常见于旧群聊摘要，不能据当前提问者或查询目标补归属 |
| `multiple_subject_ids` | 记录涉及多人，不能把整条内容都归给某一账号 |
| `invalid_hit_metadata` / `invalid_subject_ids` / `invalid_subject_id` | 结构或人物 ID不满足校验条件 |
| `subject_mapping_unavailable` | 无法从当前平台人物表得到唯一且一致的真实账号 |
| `no_current_session_presence` | 没有当前会话内归属一致的原始记录，不能暴露群外账号 |

`fallback_applied=false` 不是归属认证。当前宿主的内部人物过滤可能在无匹配时返回原候选，这不一定反映在显式降级字段里；每条命中的主体仍须独立核验。

## Replyer 如何拿到同一份说明

当前原生普通 Replyer 不完整继承 Planner 的工具调用/结果上下文。插件给已对应的工具记录附带一个不透明引用：

```text
[stable_identity.memory_ref:v1:32位随机引用]
```

Planner 在使用该材料生成原生 `reply_reference` 时可保留引用。Replyer Hook 只从这个正式参数取引用，再检查同一会话、账号/路由及工具记录，并重新回查来源；不改写原生 reply 参数，也不从用户正文读取引用。

引用由本次插件实例绑定，最多 256 个、两分钟有效。跨群、换账号/路由、过期或重启后均失效。缺少引用时不选择“最近一次记忆检索”。因此模型未保留引用、复古/压缩丢失来源等路径仍不能宣称已全覆盖。

0.2.6 修正了旧版把空参数当成引用缺失的行为：宿主普通回复也要求非空参考，因此只要没有实际记忆工具结果或明确核验引用，就不增加任何模型记忆说明、不查询 ToolRecord。非空参考缺引用只记录 `reference_missing` 诊断日志；原生参考和参数不改写，插件不认证其人物归属。重复执行先移除插件自己的旧说明，再重新构造，不清理用户正文或其他插件上下文。参考文字里的账号和消息 ID也不能代替已绑定的核验引用。

已检查 SDK 的正式 ReplyExtension：只有模型在原生 `plugin_options` 中选择扩展才会运行；只有实际选中扩展时，宿主才把 `_reply_id` 放入 Replyer 参数。当前 Planner 前后 Hook 也没有共同的请求关联 ID。单独注册扩展仍不能保证自动补传，插件没有强塞原生调用参数或按会话最近记录关联。彻底自动透传需要宿主增加每次 Planner 请求到原生 reply 调用、再到 Replyer 的正式关联字段，并携带明确的来源引用。

## 结构化记录开关与已有数据

当前宿主使用以下已有配置控制工具记录的完整结构：

```toml
[debug]
record_tool_structured_content = true
```

上面是**用户可选的宿主设置**，插件不会自动修改。开启会让今后的工具记录保存完整结构化结果，其中可能包含完整记忆及来源信息，应按现有私人数据保护方式管理。它不是身份认证开关，也不改变原生记忆写入规则。

若当前设置为 false，工具输出文本、参数仍可能照常保存，但 structured_content 只有 `structured_content_omitted` 标记。插件会明确输出这个限制，不能从旧记录恢复已省略的来源。开启后也只影响后续记录，不会自动补全旧记录；不需要为此清空或重建记忆。

即使不开这个选项，聊天逐条身份标注、person_id 原话查询、批量原始消息查证仍可工作。

## 资源、失败和持久化

每次请求最多检查最近 8 个明确工具结果及 8 个显式引用，每条结果最多 8 个命中、每个命中最多 12 个来源；独立总预算 700 ms、共享核验并发最多 4、补充说明最多 16,000 字符。达到预算时给出未检查状态，不阻断聊天或改写工具结果。

只读访问仍使用原来的四项权限：database.get、message.get_by_time_in_chat、message.get_by_id、person.get_id。没有私有远程接口、直接读取宿主 SQLite 文件或运行时方法替换。ToolRecord 是当前主程序公开数据库能力可读取的 SQLModel，兼容范围按该源码版本限定。

新增引用只存内存，卸载/重载后清空。来源状态每次使用时重新查询，不缓存“证据仍存在”的结论。原话工具冻结查询条件的缓存同时限制单份查询最多 32 KiB，防止异常参数占满凭据缓存。日志只记录限频状态计数，不打印账号、原文、调用 ID或引用值。

## 仍未解决

- `knowledge.search` 仍没有结构化来源；插件不把其文本当成指定人物的证据。
- 自动画像注入、启发式回想、聊天摘要及复古/压缩资料可能只有名字和摘要，没有可对应的工具记录；本版本不会从这些文本猜主体。
- 原生按人物筛选失败后退回其他候选、按昵称解析人物、记忆事实提取及自动写回的行为没有被修改。
- 旧错误记忆、缺失原始消息和孤立画像 ID不会自动修复。
- 已验证来源账号说过一段话，也不等于所述事实为真，更不保证模型正确理解引用、否定、玩笑和经历主体。

要完整覆盖上述自动路径，需要宿主正式接口透传主体与来源，并在记忆写入、检索、注入三层保持它们。当前独立插件已经利用现有正式能力增加核验，但不能据此承诺绝不认错人。
